# Claims Management — Phase 5

## Scope and authorization

The role model remains `ADMIN | AGENT`. Admin performs review actions in this phase;
no Claims Officer role was added. The assigned officer is the existing demo Admin.

| Operation | Admin | Agent |
| --- | --- | --- |
| List/read claims and history | All claims | Claims whose linked policy is assigned to the session user |
| Create claim | Any eligible ACTIVE policy | Assigned ACTIVE policies only |
| Review / approve / reject / close | Allowed by current status/version | Forbidden |
| Read/add internal review notes | Allowed | Forbidden (403) |

Ownership is derived from the current policy repository, never request `agentId`,
`createdBy` or `assignedOfficerId`. Admin-created claims on an Agent's policy are visible
to that Agent. `createdBy` is audit metadata, not the read authorization boundary.
Review notes have no Agent visibility option and remain entirely Admin-only. List/detail
DTOs and history never embed internal notes. Workflow reasons are deliberately visible
in history; the review dialog states this explicitly.

All endpoints require the existing HttpOnly cookie session. Writes additionally require
the existing `X-XSRF-TOKEN` header. The existing authentication/Policy APIs were preserved.

## Endpoints and contracts

| Endpoint | Response / behavior |
| --- | --- |
| `GET /api/claims` | `{items,total,page,pageSize}` after authorization, search/filter, stable sorting and pagination |
| `GET /api/claims/:id` | One `Claim` DTO, with officer name and optimistic `version` |
| `POST /api/claims` | Create SUBMITTED claim; returns 201 and DTO |
| `POST /api/claims/:id/transition` | Admin-only; `{status,version,reason,approvedAmount?}`; returns updated DTO |
| `GET /api/claims/:id/history` | `{items: ClaimHistory[]}`, chronological, generated by backend |
| `GET /api/claims/:id/notes` | Admin-only `{items: ReviewNote[]}` |
| `POST /api/claims/:id/notes` | Admin-only `{content}` (3–2000 non-whitespace characters); returns 201 and server-authored note |

### Listing parameters

`page` defaults to 1 (clamped to the last page); `pageSize` is 10, 25 or 50. `search` is a
trimmed, case-insensitive substring of claim number, policy number or customer name.
`status` accepts SUBMITTED, UNDER_REVIEW, APPROVED, REJECTED or CLOSED. `claimType` accepts
Accident, Theft, Fire, Medical or Other. `dateFrom` and `dateTo` are inclusive incident-date
bounds in `YYYY-MM-DD`. Multiple filters combine with AND; inverted ranges return no rows.
`sortBy` accepts claimNumber, policyNumber, customerName, incidentDate, estimatedAmount or
createdAt (default). `sortOrder` is asc or desc (default). Equal values use ascending ID
as a deterministic secondary sort. Invalid query values fall back to safe defaults.

The client receives only a page of authorized records, not all claims. Form policy lookup
reuses paginated `GET /api/policies?status=ACTIVE`, with 300 ms debounced search and the
existing backend ownership restriction; no new Policy endpoint was introduced.

### Claim creation

```json
{
  "policyId": "p-1013",
  "incidentDate": "2025-01-13",
  "claimType": "Accident",
  "description": "A fictional incident report for demonstration.",
  "estimatedAmount": 1000
}
```

`POST /api/claims` requires an `Idempotency-Key` header containing 10–100 alphanumeric or
hyphen characters. Retrying the same normalized payload with the same user/key returns
the existing record; a changed payload returns 409. Authorization/eligibility is checked
again on replay. Idempotency metadata is never returned to the client.

Policy must exist, be ACTIVE and be authorized. Incident date must be valid, no later
than the UTC current date, and fall within the policy coverage dates (inclusive). Estimated
amount must be finite, positive, at most 1 trillion USD and have at most two decimal places.
Description requires 10–2000 trimmed characters. IDs, numbers, customer/policy names,
reported/created/updated times, status, approved amount, officer, author and history are
server-managed; overposted values cannot override them.

The form prevents repeated clicks and marks a successful submission before navigating.
If a network/5xx response leaves the outcome uncertain, the input area becomes inert and
Retry resends the frozen report/key. This prevents a retry from creating a second report
with later edits. Definitive validation/authorization failures leave fields editable.
Idempotency keys are scoped to the current page session; after leaving/reloading during an
uncertain outcome, check the list before starting a new report.

## State machine and audit trail

Allowed transitions only:

- SUBMITTED → UNDER_REVIEW
- UNDER_REVIEW → APPROVED or REJECTED
- APPROVED → CLOSED
- REJECTED → CLOSED

CLOSED is terminal; there is no reopening, deletion or arbitrary claim editing endpoint.
Rejection requires a trimmed reason of 3–2000 characters. Approval requires a positive,
two-decimal USD amount no greater than the estimate. Approval/closure does not process
payment. A transition requires the reviewed `version`, increments it, and appends a
history record in the same serialized repository mutation. Concurrent/stale transitions
return 409 and cannot append duplicate history. Transition timestamps increase monotonically
per claim, including same-millisecond updates. Claim creation records the initial
null → SUBMITTED history entry. Client-supplied history/author metadata is ignored.

Errors retain `{status,message}`: 400 for malformed request/key, 401 for no session, 403
for ownership/review/notes/XSRF permissions, 404 for missing claim/policy, 405 for unsupported
methods (including history writes), 409 for stale/invalid transitions or conflicting keys,
422 for validation, and 500 for unexpected persistence errors.

## Angular architecture

The Claims feature retains existing file names/routes and replaces its placeholder page.
Standalone OnPush-by-default components separate filters/table, status badges, timeline,
internal notes and the confirmation/rejection dialog. Pages use feature-scoped stores:

- `ClaimsStore`: signals for results/loading/errors/query and computed empty/filter state.
  URL parameters own list state. RxJS combines route and retry streams; `switchMap` cancels
  obsolete requests. Filter/sort changes reset the page; pagination preserves query state.
- `ClaimCreateStore`: typed Reactive Form, selected policy, eligible policy page/search,
  saving/error/success and uncertain-outcome state. A group validator checks the selected
  ACTIVE policy and incident coverage. Backend repeats all validation.
- `ClaimDetailsStore`: selected claim, history/notes, loading/errors and computed permitted
  actions. Initial reads use `forkJoin`; Agent requests never include the notes endpoint.
  Successful transitions refresh server history; successful notes append only the confirmed
  server DTO. Failed note saves preserve entered content. Old mutation responses cannot
  overwrite another claim after route navigation.

`ClaimsApi` contains typed HttpClient calls. Forms use `emitEvent:false` on URL restoration
to avoid navigation loops. Search uses `debounceTime(300)`/`distinctUntilChanged`, and all
component/store subscriptions use `takeUntilDestroyed`. Unlike React controlled fields,
Reactive Forms own input values/validation/touched state while signals expose async/UI state.

## Persistence and limits

The development server stores claims/history/notes together in ignored
`mock-api/.data/claims.json`. An atomic temporary-file rename and serialized mutation queue
publish data only after persistence succeeds. All 90 seed claims and notes are fictional.
Seed claims refer to eligible existing seed policies; no seed policy is altered. Tests use
isolated temporary files and verify restart persistence.

This repository supports one mock server process, not a multi-process production database.
Policies and claims use separate files; future policy deletion/reassignment workflows will
need cross-entity transactions/referential constraints. Current ACTIVE policies cannot be
edited/deleted by the existing Policy draft endpoints. Sessions still reset on restart.
There is no file upload, officer assignment UI, Claims Officer role, payment processing or
next-phase functionality. Currency remains the project's demo USD convention. Tables scroll
inside a bounded, focusable region on narrow screens. No manual visual browser review is
claimed. Production build still needs Google Fonts network access and retains the existing
initial bundle warning; budgets were not increased.
